# Эксплуатация и восстановление

## Контуры

Staging: library-app 192.168.77.10 и library-db 192.168.77.11. Системный сервис использует PostgreSQL 15 на отдельной машине; контейнерный выпуск использует PostgreSQL 16 в собственном volume. Это разные базы.

Production для проверки Ansible: devops-clean-app 192.168.78.10 и devops-clean-db 192.168.78.11. Настройки и пароль отделены от staging.

Контейнерный API доступен через Nginx на `127.0.0.1:8080`, Grafana — `127.0.0.1:3000`, Prometheus — `127.0.0.1:9090`, registry — `127.0.0.1:5000`. Для доступа с рабочего компьютера используется SSH-туннель. Порты БД и экземпляров API не публикуются.

## Приёмка релиза

1. Задача, feature-ветка, локальный `make verify`, Pull Request и CI.
2. Для контейнерных изменений обязателен `make container-check` на Linux с Docker Engine.
3. Успешный CI основной ветки публикует SHA-образ и архив этого же образа.
4. CD передаёт архив отдельной учётной записи deployer; сервер загружает его в локальный registry и получает образ по SHA. Сборка на сервере не выполняется.
5. Проверяются контейнерные healthcheck, HTTP `/health`, точная версия `/version`, создание каталога, выдача, конфликт повторной выдачи и возврат.
6. Только после успешного сценария обновляются `/var/lib/library/deployed-sha` и `/var/lib/library/release.env`.

В workflow Deploy selected release можно вручную передать полный SHA ранее опубликованной версии. Успешный main CI обязателен и для ручного выпуска. Блокировка workflow и `flock` на сервере исключают пересечение развёртываний. Откат образа не откатывает схему: перед несовместимыми миграциями нужны отдельный план и резервная копия.

Для эксплуатационных команд загружать оба файла окружения:

```bash
cd /opt/library-deploy
docker compose --env-file /etc/library/container.env \
  --env-file /var/lib/library/release.env ps
```

Не выполнять `down -v` для рабочего проекта и `--remove-orphans` без проверки дополнительных Compose-файлов: monitoring и registry используют тот же проект.

## Диагностика

Начать с `/health`, `/version`, `docker compose ps`, `journalctl -u library` и `docker compose logs --tail=100 app db nginx`. Для контейнерных команд использовать файлы окружения из примера выше. Проверить свободное место `df -h`, inode `df -i`, память `free -m`, слушающие порты `ss -lntp` и firewall. Не выводить содержимое секретных env-файлов в отчёт или журнал.

| Симптом или отказ | Подтверждение причины | Восстановление |
|---|---|---|
| БД остановлена | `/health` 503, `library_database_up=0`, состояние db | Запустить db, дождаться healthy; проверить выдачу и возврат |
| Неверная конфигурация | Ошибка старта в журнале, отличие от шаблона | Применить Ansible либо исправить закрытый файл; пересоздать app и проверить релиз |
| Заполнен диск | `df -h`, `df -i`, ошибки записи PostgreSQL | Освободить проверенные ненужные журналы/кэш; рабочий volume не удалять; проверить БД |
| Контейнер перезапускается | RestartCount, события Docker, журнал приложения | Устранить причину старта, проверить зависимости и healthcheck |
| Превышен лимит памяти | `docker inspect`: OOMKilled, `docker stats`, метрики RAM | Откатить дефект, затем обосновать лимит; не отключать ограничение вслепую |
| Ошибка новой версии | SHA `/version`, ошибка сценария CD | Вручную выпустить предыдущий принятый SHA и повторить сценарий |
| Нарушены права | Permission denied, `stat`, пользователь процесса | Восстановить владельца/режим Ansible; не применять chmod 777 |
| Порт недоступен | `ss`, iptables, upstream Nginx, `up` | Восстановить сервис/управляемое правило; не открывать БД наружу |
| Служебная проверка ошибочна | HTTP-код и тело health, healthcheck контейнера | Исправить проверку отдельным изменением; не отключать её |
| Секрет появился в журнале | Ограниченно проверить конкретный журнал | Отозвать секрет, заменить закрытые переменные, ограничить/очистить копии журнала, добавить регрессионную проверку |

Журналы приложения содержат время, уровень, событие, шаблон маршрута, HTTP-код, длительность и request ID. Заголовки, тело, строка запроса и параметры авторизации не записываются. Для поиска одного обращения сопоставлять `X-Request-ID` ответа и `request_id` JSON-записи.

Prometheus обнаруживает оба экземпляра через DNS. Панель Grafana `library` показывает доступность, нагрузку, 5xx, p95, CPU, RAM, диск, состояние БД и активные выдачи. Предметная метрика берётся через `max`, поскольку оба экземпляра читают одну БД. При отказе БД её значение — NaN, а не ложный ноль.

Правила: отсутствие всех экземпляров одну минуту — критическая ошибка; менее двух экземпляров одну минуту — предупреждение; недоступность БД 30 секунд — критическая ошибка. Проверять состояние правил в Prometheus `/alerts` и `/api/v1/alerts`.

## Проверка изменений инфраструктуры

Workflow Configure infrastructure принимает staging или production и запускается только из main. Настройки GitHub environment infrastructure дополнительно разрешают только main. Приватный административный ключ хранится в защищённой переменной; секретные параметры находятся в `/etc/library` на контроллере. Публичный ключ и пароли БД передаются playbook из закрытого файла.

После применения обязательны успешный healthcheck и второй запуск с `changed=0`. Для проверки отклонения изменить только несекретный управляемый параметр, применить playbook, проверить восстановление и повторить запуск. Не редактировать пароль ради демонстрации отклонения.
