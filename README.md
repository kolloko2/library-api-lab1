# Library API — лабораторные работы 1–8

Минимальная информационная система для учёта библиотечного фонда. Проект выполняют студенты группы **241-372**: Кодзаев Николай, Парамонычева Анастасия, Палехова Мария.

Репозиторий: <https://github.com/kolloko2/library-api-lab1>

## Назначение и пользователи

Система хранит авторов, книги, филиалы и физические экземпляры. Библиотекарь ведёт каталог и выдачи; читатель ищет книги и получает доступный экземпляр; администратор настраивает сервис и контролирует его состояние.

Основные сценарии: добавить автора и книгу, зарегистрировать филиал и экземпляр, найти книгу, отфильтровать доступные экземпляры, выдать экземпляр читателю и оформить возврат.

## Запуск

Серверные проверки описаны в [журнале лабораторных](docs/LABS_STATUS.md), порядок выпуска и восстановления — в [инструкции эксплуатации](docs/OPERATIONS.md).

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env  # Linux/macOS: cp .env.example .env
python -m alembic upgrade head
uvicorn app.main:app --reload
```

После запуска: Swagger UI — `http://127.0.0.1:8000/docs`, проверка состояния — `GET http://127.0.0.1:8000/health`.

## Правила внесения изменений

1. Для изменения создаётся задача (Issue) и ветка `feature/<issue>-<name>` от актуальной `main`.
2. Коммиты должны быть небольшими и осмысленными; сообщение начинается с `feat:`, `fix:`, `docs:`, `test:` или `chore:`.
3. Перед отправкой обязателен `make verify`: анализаторы, тесты, покрытие, компиляция, аудит зависимостей и проверка мутации. Для контейнерных изменений дополнительно выполняется `make container-check`; для Ansible — проверка синтаксиса, применение и повторный запуск без лишних изменений.
4. Изменение принимается через Pull Request после проверки владельцем кода и успешных обязательных CI-заданий verify, containers и secrets. Изменения тестов, правил приёмки и инфраструктуры требуют review CODEOWNERS.
5. Запрещено коммитить `.env`, базы данных, виртуальное окружение, токены и пароли; запрещено напрямую переписывать историю `main` и выполнять force-push в неё.
6. После приёмки PR сливается в `main`; стабильная версия отмечается аннотированным тегом.

Конфигурация читается из переменных окружения. Файл `.env.example` содержит только безопасный шаблон; настоящий `.env` игнорируется Git.

Нельзя удалять тесты, снижать порог покрытия, отключать анализаторы или healthcheck ради прохождения приёмки. Запрещены секреты в образе, тег latest, запуск приложения от root и публикация лишних портов.

После успешного main CI образ получает тег полного SHA. CD развёртывает его на отдельном staging, проверяет контейнеры, версию и полный сценарий выдачи/возврата. Ручной откат выполняется workflow Deploy selected release с SHA ранее принятой версии. Инфраструктура двух окружений применяется workflow Configure infrastructure. Конфигурации Prometheus, Grafana, Nginx и Ansible хранятся в infra.
